# 02 — Port Platform Configuration

## Gate

Require passing `handoff-status/01-target-generated.yaml`. Work only in the fresh target repository. Do not mutate the running cluster.

## Ownership rule

`mappings/template-overlap.yaml` is authoritative. For each overlap:

1. Read the generated target implementation completely.
2. Read the corresponding payload implementation.
3. List meaningful differences.
4. Keep the generated template resource as the sole owner.
5. Carry only a difference required to preserve the approved topology or behavior.

Never copy the old bootstrap tree over the generated template. Never create duplicate Flux Kustomizations, HelmReleases, Gateways, certificates, or chart sources for one component.

## Template-owned review order

Review and commit in these groups:

1. Talos/bootstrap generation.
2. Cilium, CoreDNS, metrics-server, Spegel, and Reloader.
3. cert-manager.
4. Flux Operator and FluxInstance.
5. Envoy Gateway, k8s-gateway, Cloudflare DNS, and Cloudflare Tunnel.
6. Replace the generated echo example with the current `payload/apps/default/echo` behavior.

Use each `requiredComparison` entry in `mappings/template-overlap.yaml`. Important current deviations include Cilium native routing, DSR/Maglev, L2 announcements, Hubble, Gateway addresses, wildcard TLS, redirects/compression/HTTP3 policies, and Flux webhook routing.

## Add non-template platform applications

Use only records in `mappings/source-to-target.yaml` with `owner: migration-payload` and waves 1–4. Port them into the generated repository's existing application layout and namespace registration pattern.

Ordered groups:

- External Secrets operator.
- 1Password Connect, then ClusterSecretStore.
- Longhorn and CloudNativePG.
- VictoriaMetrics operator, VPA, Coroot operator, and ARC controller.
- VictoriaMetrics/VictoriaLogs/Grafana/Goldilocks/Kubetail monitoring resources.
- Consul, Consul Sync, `cloudflare-dns-internal`, and remaining supporting integrations.

For each application:

- use its `targetPath`, namespace, wave, and resolved dependencies from the mapping;
- adapt the Flux GitRepository identity/path to the generated repository;
- register its `ks.yaml` in the namespace kustomization exactly once;
- preserve cross-namespace `dependsOn` namespaces;
- preserve `${SECRET_DOMAIN}` substitutions using the generated target secret mechanism;
- retain chart versions and behavior initially unless the pinned template API requires an explicit compatibility change;
- document every compatibility change in `handoff-status/02-platform-ported.yaml`.

Do not copy or enable application Secret ciphertext until the secrets session has assigned a new Age recipient.

## Validate after each group

Use the target repository's pinned tools and CI commands. At minimum:

```bash
just configure
```

Then render the root Flux path with the validation mechanism generated by the pinned template. Validate that every referenced path exists and that no resource has two owners.

Compare mapped platform IDs with files in the target repository. A platform ID is complete only when its target path exists, its namespace registration includes it, and its sources/dependencies resolve offline.

## Stop conditions

Stop on duplicate ownership, unresolved source/path/reference, missing CRD owner, SOPS plaintext, chart/API incompatibility, or generated-template validation failure. Do not work around an error by deleting a dependency edge.

## Completion artifact

Write and commit `handoff-status/02-platform-ported.yaml` with each overlap decision, every wave 1–4 platform ID, target path, validation result, documented compatibility changes, and `clusterMutationPerformed: false`.
