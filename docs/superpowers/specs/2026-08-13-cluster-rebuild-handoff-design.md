# Cluster Rebuild Handoff Package Design

## Purpose

Create a self-contained, security-conscious handoff package that another agent can use in independent sessions to rebuild the existing four-node Talos cluster from a fresh repository generated by `onedr0p/cluster-template`, then redeploy the same GitOps-managed applications and non-secret configuration.

The package is a migration aid, not the target repository itself. It preserves this repository and does not modify the live cluster.

## Decisions

- Create a fresh target repository; do not transform this repository in place.
- Pin the target template to commit `bb09348610aa5bee9505230b99c21c08db15bf6d` from 2026-08-13.
- Reuse the current four machines and network identities:
  - `node1` through `node4`
  - node addresses `10.69.0.10` through `10.69.0.13`
  - Kubernetes API VIP `10.69.0.25`
  - pod CIDR `10.42.0.0/16`
  - service CIDR `10.43.0.0/16`
  - internal gateway `10.69.0.27`
  - DNS gateway `10.69.0.26`
  - external gateway `10.69.0.28`
  - existing node MAC addresses and Talos install-disk selections
- Migrate configuration only. PersistentVolume contents, databases, object data, and other application state are intentionally not migrated.
- Redeploy all GitOps-managed applications, including applications with known operational impact such as Open-Meteo. Risks are documented rather than silently changing behavior.
- Use new empty volumes and databases for stateful applications.
- Keep all agent sessions independent by supplying self-contained prompts with explicit inputs, outputs, gates, and verification commands.

## Non-Goals

- Backing up or restoring Longhorn volumes, databases, application files, or the etcd snapshot.
- Preserving runtime-only drift that is not represented in Git.
- Reusing plaintext private keys, kubeconfigs, Talos credentials, or other workstation credentials in the package.
- Automating destructive wipe or bootstrap actions from this repository.
- Building a general-purpose repository conversion framework for future migrations.
- Changing application behavior, resource sizing, chart versions, or architecture unless required for compatibility with the pinned template.

## Deliverables

Implementation will produce:

1. `handoff/cluster-rebuild/`
2. `handoff/cluster-rebuild.tar.gz`
3. `handoff/cluster-rebuild.tar.gz.sha256`
4. A completion report listing package contents, verification evidence, identified risks, and external prerequisites.

## Package Components

### Start document and manifest

`START-HERE.md` is the entry point for a human or agent. It states the scope, source and target revisions, security boundary, session order, destructive gates, and expected outcome.

`manifest.yaml` records:

- package format version;
- generation timestamp;
- source repository revision;
- pinned target-template repository and revision;
- included artifact paths and roles;
- source inventory counts;
- explicit exclusions;
- required verification results.

### Inventories

`source-cluster.yaml` records the reusable non-secret cluster topology, Talos image schematic reference, Kubernetes versions where observable, network ranges, virtual IPs, storage classes, and foundational platform choices.

`applications.yaml` contains one record for every application discovered from `kubernetes/apps/*/*/ks.yaml`. Each record includes source path, namespace, Flux Kustomization identity, chart or manifest source, image references where statically available, storage use, routes, services, secret dependencies, and expected fresh-state behavior.

`dependencies.yaml` records Flux `dependsOn`, source references, `valuesFrom`, `substituteFrom`, Gateway parent references, namespace dependencies, CRD/operator dependencies, and deployment wave.

`secrets-and-prerequisites.yaml` records secret names, ExternalSecret remote item and field references, SOPS-encrypted source files, required external systems, and the action needed in the new repository. It never records secret values.

`live-snapshot/` contains timestamped, sanitized observations of nodes, namespaces, Flux objects, workloads, services, Gateway API routes, storage classes, and PVC metadata. It exists to compare desired-state inventory with the running cluster, not to preserve runtime drift.

### Payload

`payload/apps/` contains sanitized copies of application desired-state manifests that the implementation agent can adapt into the generated target repository.

`payload/components/` contains reusable non-template components. Template-owned platform resources are excluded from this payload unless a current setting is an intentional deviation that must be represented as an overlay or documented mapping.

`payload/cluster.toml.example` is prefilled with the approved non-secret topology and network values. Repository URL, domain, DNS credentials, and other values that cannot be safely derived are clearly marked as values the implementation agent must obtain through an authorized channel.

### Mappings

`template-overlap.yaml` assigns ownership for every overlapping component. The pinned template owns Talos generation and its generated Cilium, CoreDNS, Spegel, cert-manager, Flux, Envoy Gateway, external DNS/tunnel, and Reloader resources. The migration carries only intentional deviations after comparing the generated target with the current configuration.

`source-to-target.yaml` maps every source application and reusable component to its intended target location, owner, deployment wave, required adaptations, and verification checks.

### Runbooks

The runbooks form an ordered, gate-driven workflow:

1. `00-preflight.md`: verify hardware facts, target repository access, required external systems, inventory completeness, and package integrity. No cluster mutation is allowed.
2. `01-generate-target.md`: create a fresh repository from the pinned template, populate `cluster.toml`, run template generation, and validate the generated baseline.
3. `02-port-platform.md`: compare overlapping components, retain template ownership, and migrate only non-template platform services or intentional deviations.
4. `03-port-apps.md`: port applications in dependency waves and adapt paths, namespaces, sources, substitutions, routes, and storage declarations.
5. `04-recreate-secrets.md`: create a new SOPS/Age trust chain, reconnect External Secrets and 1Password, re-encrypt necessary values, and prove secrets can reconcile without exposing them.
6. `05-cutover-bootstrap.md`: require explicit user authorization, wipe and bootstrap Talos, bootstrap template applications, and allow Flux to reconcile in ordered waves.
7. `06-verify.md`: check cluster health, Flux readiness, inventory parity, routes, certificates, DNS, new storage provisioning, and application reachability.

### Session prompts

Each prompt is independently usable in a new agent session. It includes:

- purpose and boundaries;
- required package paths and predecessor artifacts;
- allowed target-repository changes;
- ordered actions;
- stop conditions;
- expected output files;
- exact verification evidence;
- a rule not to infer missing secrets or destructive authorization.

Prompts are divided at meaningful state boundaries: target generation, platform port, application port, secrets readiness, cutover/bootstrap, and post-bootstrap verification.

## Ownership and Migration Workflow

### Template-owned baseline

The implementation agent starts from generated output, not copied legacy bootstrap files. The pinned template owns components it already generates. Current settings are compared against generated settings, and only required differences are applied using the target repository's conventions.

This avoids creating a second convention beside the template and prevents duplicate ownership of foundational resources.

### Deployment waves

Non-template resources are introduced in dependency order:

1. Template bootstrap and Flux reconciliation.
2. External Secrets and 1Password integration.
3. Storage and database operators, including Longhorn and CloudNativePG.
4. Observability and supporting operators, including VictoriaMetrics, VictoriaLogs, Coroot, VPA/Goldilocks, and ARC.
5. Supporting network services not replaced by the template.
6. Applications without stateful dependencies.
7. Stateful applications using newly provisioned empty storage.
8. Applications with explicit cross-application dependencies, such as Weather Scraper after Open-Meteo.

The inventory, rather than this high-level list, is authoritative for the exact application set and dependency edges.

### Secrets handling

The package may include encrypted SOPS manifests only if they remain ciphertext and contain no embedded private key. It does not include the current Age private key. The target repository creates a new Age key pair and re-encrypts required cluster values for the new recipient.

ExternalSecret definitions and non-secret 1Password item/field references may be copied. The target must prove access to 1Password and other external providers before destructive cutover.

Credentials found on the source workstation are treated as sensitive source material, not migration payload. The runbook identifies them by purpose only and recommends rotation where the rebuild changes trust boundaries.

### Stateful workloads

Every workload that declares persistence is labeled `fresh-empty-state` in the application inventory. The runbook must not imply that recreating a PVC restores its former contents.

Applications that require initialization credentials or schema creation receive those through the recreated secret pipeline and their normal controllers or startup behavior. If an application cannot initialize cleanly without old data, the implementation agent stops and reports the incompatibility rather than fabricating a migration.

## Safety and Error Handling

Package generation is read-only with respect to the live cluster and current desired state.

The cutover runbook blocks destructive action unless all of these conditions are met:

- the fresh target repository exists and is reachable by Flux;
- template rendering and repository validation succeed;
- source and target application inventories reach parity;
- required external secret providers and DNS/ingress prerequisites are available;
- hardware and network values are complete;
- the package checksum passes;
- the user explicitly authorizes destruction in the cutover session.

A failed gate stops the workflow. The agent records the failure and evidence; it does not bypass the gate, guess credentials, or mutate the existing cluster to make the package appear complete.

Because application data is intentionally excluded, rollback restores only cluster and application configuration. It cannot restore previous application state after the old disks or volumes are wiped.

## Verification and Acceptance Criteria

The package is complete only when all of the following are demonstrated:

- Every source `ks.yaml` application appears exactly once in `applications.yaml` and `source-to-target.yaml`.
- Every payload file is declared in `manifest.yaml` and covered by `checksums.sha256`.
- The final archive extracts successfully and its sidecar SHA-256 checksum matches.
- No kubeconfig, Talos secret, Age private key, deploy private key, Cloudflare credential JSON, token file, etcd snapshot, Kubernetes Secret value, or decrypted SOPS content exists in the package.
- The pinned template revision is recorded and reachable.
- All discovered `dependsOn`, `sourceRef`, `valuesFrom`, `substituteFrom`, ExternalSecret references, namespaces, and Gateway parent references are represented in the inventories.
- Every persistent workload explicitly records that it starts with empty state.
- Live snapshots contain metadata only and no Secret values.
- Every prompt declares prerequisites, outputs, stop conditions, and verification commands.
- No package-generation step changes the current cluster or its GitOps desired state.

## Known Operational Risks to Surface

- Open-Meteo's sync container can generate sustained high ingress traffic from S3; its current configuration is preserved but flagged.
- Reusing node and virtual IPs prevents old and new clusters from running concurrently on the same network, so the rebuild is an offline cutover.
- Four control-plane nodes create an even etcd member count; the package preserves topology as requested but records this availability tradeoff for the implementation agent.
- Current stateful services will start empty, including databases and object/application storage consumers.
- Current local workstation files include credentials and recovery material that must never enter the package or target repository in plaintext.
- Template APIs, chart sources, and conventions may differ from legacy manifests; compatibility adaptations must be explicit in `source-to-target.yaml`.
